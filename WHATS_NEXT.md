# What's Next

## What This Is

`encryptedcol` is a standalone Go library (`github.com/ai8future/encryptedcol`, Go 1.24+, currently **v1.0.3**) that provides client-side, column-level encryption for PostgreSQL/Supabase applications, with HMAC-based blind indexing so encrypted fields stay exact-match searchable. It is the "column-confidentiality layer" of Cliff's **db_sql_suite** (sibling to `tablebox`, the suite's multi-tenant data-ingestion platform), and ships with no database-driver dependency so any Go service can adopt it. It serves Go backend/repository-layer developers who need to keep PII, financial, or health data encrypted at rest — e.g. under GDPR/HIPAA/PCI-DSS/SOC 2 — while preserving login/dedup/search workflows.

## Current State

**Maturity: feature-complete, well-tested library with zero known consumers.** This is not an MVP or prototype — it's the finished implementation of its own design doc, sitting unused.

- All 9 phases of `db_crypted_implementation_plan.md` are implemented and match the shipped files: `cipher.go` (Seal/Open/BlindIndex), `kdf.go` (HKDF-SHA256), `options.go`, `provider.go` (`KeyProvider` + `StaticKeyProvider`), `compress.go` (zstd with buffer pooling, 64MB zip-bomb cap), `blindindex.go`, `normalize.go` (6 normalizers), `search.go` (SQL builder with column-name validation and PostgreSQL param-limit guards), `helpers.go` (string/JSON-generic/int64/pointer variants), `rotate.go`, `format.go`, `errors.go`, `doc.go`.
- Verified directly: `go build ./...` and `go vet ./...` both pass clean, and `go test -cover ./...` reports **97.4% coverage** (matches the CHANGELOG's claim). 14 test files, table-driven style with `testify/require`, plus benchmarks. No `TODO`/`FIXME`/stub markers anywhere in the source tree.
- **Snappy is the one openly-incomplete corner**: the wire format reserves flag `0x02` and `WithCompressionAlgorithm("snappy")` is accepted by the options API, but `compress.go`'s `decompress()` does not implement it — selecting it fails at runtime, not compile time (confirmed via `compress_test.go:TestDecompress_Snappy` and `cipher_test.go:TestOpen_SnappyFlagUnsupported`, both asserting an error).
- **No `integration_test.go` exists**, despite Phase 8 of the implementation plan explicitly calling for one against a real PostgreSQL instance. Every test operates on in-memory byte slices — nothing has verified the documented `BYTEA` + composite `(key_id, x_idx)` B-tree index behavior against an actual database.
- **No `examples/` directory** (Phase 9 asked for `examples/basic`, `examples/repository`, `examples/migration`); only inline `example_test.go` godoc examples exist.
- **No CI**: there is no `.github/` directory, so `go build`/`go vet`/`go test -race -cover` are run manually, not gated on push/PR.
- **This directory is not a git repository.** `git status` fails with "fatal: not a git repository" both here and at the `db_sql_suite` parent, even though `AGENTS.md` assumes an auto-commit-and-push workflow after every change and the module path implies a `github.com/ai8future/encryptedcol` remote. I could not determine why version control is absent at this path.
- **Zero consumers found**: a repo-wide grep for `ai8future/encryptedcol` imports across `/Users/cliff/Desktop/_code` (including its own suite sibling `tablebox`) returned nothing. The library is fully built but not wired into anything.
- The `_rcodegen/` folder (filenames only — its contents are out of scope per `AGENTS.md`) contains roughly 35 dated audit/fix/refactor/quick-review reports from Claude, Codex, and Gemini spanning Jan 19–28, 2026, and `docs/plans/` holds two dedicated "audit fixes" plans (2026-01-19, 2026-01-22) that addressed real issues (dead code in default-key selection, a key-material reference leak in `StaticKeyProvider.GetKey`, a division-by-zero edge case in compression). The code has been through many rounds of adversarial AI review already — its polish is earned, but that also means another generic "audit this" pass is likely low-yield now.

## Product Opportunities

1. **Dogfood it inside the suite.** The library has never been integrated into a real repository layer — not even `tablebox`, its own sibling. Until something actually calls `SealStringIndexedNormalized`/`SearchCondition` against a live schema, core design bets (e.g., "all encrypted columns in a row share one `key_id`," which forces whole-row re-encryption on rotation) are unvalidated against real multi-tenant, heterogeneous-schema data.
2. **Close the Postgres integration-test gap.** This is the one category of testing the original design explicitly called for (Phase 8) and never got. A real database round-trip test would retire the largest unverified claim in the docs: that a standard B-tree index on the `(key_id, field_idx)` composite "works efficiently."
3. **Ship reference `KeyProvider` adapters (Vault / AWS or GCP KMS).** `PRODUCT.md` markets "integrate with enterprise key management" as a core capability, but only `StaticKeyProvider` exists today — every adopter has to write their own Vault/KMS glue from the bare 3-method interface. Thin, optional adapter packages (separate `go.mod` submodules, so the core module keeps its "no dependency" purity) would convert a documented interface into an actual adoption unlock.
4. **Reduce repository-layer boilerplate.** `db_crypted_design.md` explicitly rejected `sql.Scanner`/`driver.Valuer` wrappers in favor of the repository pattern, arguing "the verbosity is worth the clarity." That verbosity — manual `Seal`/`Open`/`BlindIndex` calls per field, per query — is exactly the friction a compliance-driven adopter feels first. A small, struct-tag-driven code generator (e.g. `encryptedcol:"indexed,normalize=email"`) that emits plain Go repository glue (no runtime reflection magic) would keep the documented design philosophy while removing its stated cost.
5. **Get a review that isn't another AI self-audit.** The `AGENTS.md` "anti-patterns" section exists because automated auditors keep re-flagging the same three intentional choices (static HMAC blind index, panic-on-`crypto/rand`-failure, dual key-ID). Combined with ~35 already-run internal audit cycles, that's a strong signal the AI-review well is close to dry. Given `PRODUCT.md`'s "we cannot read your data even if breached" claim targets HIPAA/PCI-DSS/SOC 2 buyers, that claim deserves a review channel that isn't the same tools re-checking their own homework.

## Risks & Open Questions

- **No validated consumer.** Without real integration, it's unknown whether the "one `key_id` per row" design (which forces whole-row re-encryption on rotation, by explicit design choice in `db_crypted_design.md`) holds up for a multi-tenant, heterogeneous-schema workload like `tablebox`'s. This could force an API change that's much cheaper to discover now than after adapters/tooling are built on top.
- **Missing git history is unexplained.** I could not determine from the code whether this is a fresh checkout that lost its `.git`, a deliberate export, or something else. Any claims about production usage, deployment history, or how "v1.0.0 stable" (Feb 2026, per CHANGELOG) was actually decided rest entirely on `CHANGELOG.md`'s own self-reported entries — I could not independently verify them.
- **Diminishing-returns signal on further AI auditing.** ~35 dated audit/fix/refactor reports from three different AI tools within roughly ten days (per `_rcodegen` filenames), plus two `docs/plans/` audit-fix plans, suggest most low-hanging correctness findings are already absorbed. The risk is spending more effort re-running that same review loop instead of pursuing the untested integration/consumer question, which is the actual unknown.
- **Documented, accepted crypto trade-offs remain unresolved for compliance buyers.** The compression oracle (ciphertext length still correlates with plaintext length) and blind-index frequency leakage on low-entropy fields are both called out in the README/PRODUCT.md as intentional, accepted limitations — not bugs — but a HIPAA/PCI-DSS auditor evaluating this for a real deployment will ask about them, and today the only answer is "we documented it."
- **Snappy is a selectable-but-nonfunctional option.** `WithCompressionAlgorithm("snappy")` is accepted by the public API, but any ciphertext produced with it (or any format byte `0x02` encountered) fails to decompress. Worth deciding whether to remove the snappy option from the public surface until implemented, rather than leave a footgun in `options.go`.
- **Adoption risk underlies every "build an adapter/tool" opportunity above.** This is a well-crafted, generic building block, but KMS adapters and codegen are wagers that someone will actually use the library. With zero current consumers in this workspace, confirm there's a real near-term consumer (`tablebox`? the `Airborne`/`Dispatch` projects named in `db_crypted_design.md`? an external customer?) before investing further in tooling nobody has asked to use yet.
